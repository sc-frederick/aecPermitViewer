## Findings

### A01. Make migration backups include committed WAL data

[store.ts:109](../src/main/store.ts#L109) reads the schema version, closes a read-only connection, and copies only the main database file at line 117. A committed transaction can still reside in SQLite's `-wal` file after an abnormal exit. Opening and closing that read-only connection did not make the copied file complete in the reproduction.

Reproduction: create and close a database, then use a child process to open it in WAL mode, set `user_version = 2`, insert a permit, and exit without closing SQLite. Open `PermitStore` to migrate it. The live database contains `committed-before-exit`; its generated `.before-v3-*.bak` contains no permit rows. The backup is incomplete even though the migration itself succeeds. No concurrent writer is required.

Use a SQLite-aware backup operation that produces a coherent standalone database. Add a restore test that starts from committed, uncheckpointed WAL data and verifies the restored rows. The existing migration tests close their connections normally, which misses this case.

### A02. Read workflow evidence before claiming the authority has the next step

[action.ts:26](../src/shared/action.ts#L26) assigns Hillsborough `In Process`, Tampa `In Process`, and St. Petersburg `IN PROCESS` to the authority. The AEC filter then excludes them. The worker reads record identity and headline status without the workflow information needed to resolve responsibility.

The repository's [status survey](PERMIT_STATUSES.md#L41) records Hillsborough `HC-BLD-25-0076688` as `In Process` while Application Review awaits a client reply. It also explains that [St. Petersburg Plan Tracking](PERMIT_STATUSES.md#L70) can contain outstanding corrections or pickup steps under `IN PROCESS`. These are existing survey observations, not newly verified live records.

This remains the open F01/F02/F08 work. Capture dated task/agency evidence, distinguish outstanding requests from superseded requests, and retain uncertainty when that evidence is unavailable. Keep the verified raw status separate from the responsibility judgment. Validate the full evidence-to-badge and notification behavior against labeled cases; navigation confidence thresholds do not establish classification accuracy.

### A03. Recheck scheduling eligibility after asynchronous prerequisites

[check-queue.ts:226](../src/main/check-queue.ts#L226) checks eligibility before awaiting `readKey()`. After that await, it checks cancellation and shutdown but does not check eligibility again. `prune()` only removes queued entries; this entry has already become `current`.

Reproduction through the public queue: enqueue an eligible scheduled permit with a deferred key read, change eligibility to false, call `prune()`, then resolve the key. `start()` still receives the permit. The observed result was `{"eligible":false,"started":["permit"]}`. A user switching to manual mode, excluding the permit, or crossing the scheduling window during that wait can still trigger a check.

Recheck immediately before starting scheduled work. Also account for the later `await browserVerified` in [main/index.ts:262](../src/main/index.ts#L262). Preserve manual requests. Extend the existing queue tests with a deferred prerequisite, and cover the final browser-start boundary. This is a remaining edge in the previously completed F09 work.

### A04. Keep time-row identity until edits are validated

[renderer/index.ts:522](../src/renderer/index.ts#L522) filters empty time fields out of `editedCheckTimes()`. The remove handler at [line 1073](../src/renderer/index.ts#L1073) then splices this shortened array using the original DOM row index.

Browser reproduction: start with `08:30`, `12:30`, `16:30`; clear the first field; click Remove on the second row. The bridge receives `["12:30"]`. The time the user intended to remove survives, while `16:30` is deleted.

Keep raw rows and their identities through the edit/remove operation. Validate before committing the remaining values. Add a renderer regression that clears one field, removes a different row, and asserts the saved schedule.

### A05. Give the updater one coherent operation state

[UpdateManager.check](../src/main/updater.ts#L184) clears `available` and `downloadedPath` while a prior download can still be running. `download()` captures its payload and later assigns `downloadedPath` without checking whether that payload is still current. The [renderer update controls](../src/renderer/index.ts#L1263) disable only the button for the current action, so Check for updates remains available during a download.

Reproduction used a local HTTPS server, a generated Ed25519 key, a correctly signed manifest, and a delayed installer response. The first check found version `1.1.0`. While its download waited, a second check received HTTP 503. The first download then completed successfully, but `installerForApprovedHandoff()` failed with `No verified update downloaded`. The renderer's completion path reports that this version is ready to install.

Represent available/downloading/ready states together and serialize conflicting operations, or invalidate and cancel older operations by generation. Coordinate data deletion with downloads too. Verify delayed download plus recheck, new feed version, failure, and shutdown. Existing hash and signature checks fail closed; this reproduction did not bypass installer verification.

### A06. Translate the actual SQLite duplicate error

[main/index.ts:457](../src/main/index.ts#L457) checks `error.code === "SQLITE_CONSTRAINT_UNIQUE"`. With this repository's Node 24 runtime, adding the same permit twice through `PermitStore` produces `code: "ERR_SQLITE_ERROR"`, `errcode: 2067`, and `errstr: "constraint failed"`. The intended duplicate-permit message is therefore skipped, and the outer IPC handler returns the generic failure text.

Classify this known constraint failure in the SQLite adapter and return a tagged `AlreadyTracked` result. Test the public add operation against a real temporary database. Match structured driver information, not the error's English message.

### A07. Put errors where the active dialog can display them

The global [notice element](../src/renderer/index.ts#L133) uses [fixed positioning and `z-index: 10`](../src/renderer/styles.css#L330), outside the modal dialogs. Details and Settings use `showModal()`, which puts them above ordinary document stacking contexts.

In the actual renderer, failing Check now from an open details sheet set `notice.hidden` to false, but hit-testing at the notice's center returned `.sheet-body`. The error was behind the sheet. Install/delete failures also use this notice path while Settings remains open.

Use an error region inside the active dialog, or an intentional top-layer notification mechanism. Verify visibility rather than only checking notice text or its `hidden` property.

Separately, [loadHistory](../src/renderer/index.ts#L699) has `try/finally` without rejection handling and is invoked with `void`. Rejecting its bridge promise produced an unhandled rejection and blank history with no notice. Distinguish an empty history from a failed read, and make retry possible. Preserve the existing generation guard and request deduplication.

### A08. Validate the whole navigation answer before applying thresholds

[jev.ts:7](../src/main/jev.ts#L7) accepts any finite confidence/probability numbers. At [line 109](../src/main/jev.ts#L109), the margin uses only probabilities present in the response, so omitted alternatives cannot lower the margin.

Using `chooseNavigation()` with the real TypeSafe SDK and its configurable fetch seam, both of these answer bodies produced a chosen action:

```json
{"type":"choice","choice":"open","confidence":10,"probabilities":{"open":10,"WAIT":-5,"STOP":-5}}
{"type":"choice","choice":"open","confidence":0.9,"probabilities":{"open":0.9}}
```

The offered criteria included `open`, `WAIT`, and `STOP`. No live API call was made. The installed SDK deserializes the response without enforcing these application constraints.

Parse the response envelope and answer at the adapter boundary. Bound probabilities and confidence to their valid domain, require the offered alternatives, and check any normalization requirements against the service contract. Return a precise malformed-response outcome. Add SDK-seam cases for omitted alternatives, out-of-range values, unknown choices, weak margins, cancellation, and retry exhaustion.

### A09. Expose credential pause state in snapshots

[KeyStore.state](../src/main/key-store.ts#L26) returns `configured` when encrypted storage is available and the file exists. It does not establish that the file decrypts or that the service accepts the key. The queue separately remembers rejection and [stops scheduled enqueueing](../src/main/index.ts#L338), but [AppSnapshot](../src/main/index.ts#L161) does not carry that pause reason.

The renderer [hides the key banner](../src/renderer/index.ts#L461) for `configured`. Key notices pass through the optional failure-notification preference and are transient. After rejection, outstanding permits can continue to say `Next check now` even though scheduled checks will not resume until a key is saved. An unreadable key also leaves the persisted-file check reporting `configured`.

This is a source-traced Windows behavior, not a native encryption reproduction. Include the effective credential/check availability state in the snapshot and show a persistent recovery action. Saving a usable key should clear the pause and refresh eligibility. A scheduling prerequisite should remain visible even when optional notifications are disabled.

### A10. Prevent older snapshots from overwriting newer state

[snapshot](../src/main/index.ts#L161) reads permits before awaiting `keys.state()`. [broadcast](../src/main/index.ts#L186) clears `broadcastPending` before the asynchronous `sendSnapshot()` finishes, allowing another snapshot to overlap it. A later key-state read can finish first. The renderer applies snapshots without a revision check.

Thus an older permit list can arrive after a newer one and temporarily restore removed/stale rows, counts, or checking indicators. Settings in the same snapshot are read after the await, so a snapshot can also combine observations from different moments. This ordering was established from source; it was not reproduced using Windows key storage.

Serialize/coalesce the entire read-and-send operation, or attach a monotonically increasing revision that the renderer enforces across pushed snapshots and direct replies. Test an intentionally delayed first snapshot that completes after a second one.

### A11. Keep known failures distinct and retain diagnostics

The [IPC catch-all](../src/main/index.ts#L223) discards every caught cause. Key-storage and updater failures commonly reject with plain `Error`; the caller cannot reliably distinguish a recoverable prerequisite, invalid release data, a local filesystem failure, or a defect. A06 demonstrates a user-visible consequence.

[check-runner.ts:129](../src/main/check-runner.ts#L129) turns any rejected message handler into `api_unavailable`, even if the failure is local. At [line 123](../src/main/check-runner.ts#L123), `void rm(...).finally(markClosed)` still leaves a rejected cleanup promise unhandled if removal fails. Calling `finally` does not consume that rejection.

Introduce precise local tagged results at existing adapter boundaries, following coding-standards. Keep user-facing responses valid and record structured, redacted diagnostics with the operation, run ID, and classified cause. Handle cache cleanup failure explicitly while still settling `closed`.

Tighten related state types while touching these boundaries: [CheckResult](../src/main/check-runner.ts#L10) currently allows `success` without an observation, and the [worker protocol](../src/shared/worker-protocol.ts#L44) accepts `failed` with a success outcome and arbitrary numeric action counts. These are representable invalid states, not demonstrated worker exploits. Use discriminated outcomes and nonnegative integer counts. No framework migration is needed.

### A12. Validate and classify the update Worker's boundaries

In [the update Worker](../infra/update-server/src/index.js#L53), every R2 exception becomes HTTP 416. Calling the real handler with a bucket adapter that rejects an ordinary GET yielded `416 Range not satisfiable`, although the request had no Range header. This obscures an upstream failure and gives clients the wrong retry signal.

Other boundary gaps are visible in the same file:

- `decodeURIComponent` at line 13 can throw before routing. A malformed `%ZZ` path rejected with `URIError` rather than returning a controlled client error.
- `putManifest` at line 151 reads the whole request before enforcing its limit, and compares UTF-16 string length to a byte limit.
- Multipart completion at line 133 buffers and destructures unchecked JSON before calling R2.
- This JavaScript Worker is outside the project's TypeScript include and has no dedicated behavioral tests.

Distinguish bad ranges, malformed inputs, and storage failures. Bound incoming bytes while reading, parse the upload contracts, and add checked Worker types and local handler/runtime tests. Preserve streaming for installer bodies. These recommendations follow Cloudflare's [request/response streaming guidance](https://developers.cloudflare.com/workers/best-practices/workers-best-practices/#stream-request-and-response-bodies) and [R2 Workers API contract](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/). Upload-body exposure is limited to authenticated upload requests; this is not a claim of unauthenticated release publication.

### A13. Make release publication immutable and ordered

The [Windows workflow](../.github/workflows/windows.yml#L11) serializes runs per Git ref, so different tags can publish concurrently. The [release step](../.github/workflows/windows.yml#L101) overwrites the versioned installer and current manifest with unconditional `aws s3 cp` operations.

A rerun that produces different bytes for the same version can overwrite an installer served with a year-long immutable cache policy. An older release finishing last can replace the current feed with an older version. Client signature/hash verification remains valuable: stale bytes fail verification, and newer installed apps refuse older versions. Delivery to users who still need an update can nevertheless fail or regress to an older offering.

The manual Worker upload path guards only the installer named by the current manifest, and only when creating the multipart upload. Completion does not repeat that check, and older versioned objects can be overwritten.

Serialize publication to the shared feed and enforce a version policy at commit time. Treat every published versioned installer as immutable: accept an identical retry or reject conflicting bytes. Apply the same rules to both CI and manual publication, including multipart completion. Verify these paths with a local bucket fixture before any deployment.

### A14. Address vulnerable build dependencies deliberately

The full npm audit reports 25 affected packages: 1 critical, 20 high, and 4 low. These counts include inherited toolchain vulnerabilities, not 25 independent exploits. The flagged paths belong to build/test tooling; the production-only npm audit reports zero.

Concrete installed examples include `tar@6.2.1` nested under Electron Forge/node-gyp, `extract-zip@2.0.1`, and `tmp@0.0.33`. The [node-tar maintainer advisory](https://github.com/isaacs/node-tar/security/advisories/GHSA-23hp-3jrh-7fpw) confirms one of the reported archive-processing problems. npm reports no automatic fix for several of these dependency paths.

Review compatible upstream toolchain updates or narrowly justified replacements/overrides, then qualify packaging on Windows. Avoid an unreviewed `npm audit fix --force`. The production-only result does not assess the shipped Electron/Chromium binaries, and this audit did not demonstrate exploitation through the app.

### A15. Only remove a download file owned by the operation

[saveDownload](../src/main/updater.ts#L133) opens the destination with `wx`, but its catch block unconditionally removes the path. Supplying an existing file caused `EEXIST` and deleted the existing file's contents/path.

The normal caller uses a UUID for its temporary name, so collision exposure is low. Still, track whether this operation created the file and only unlink it in that case. Add one existing-file regression to the current stream-failure tests. Preserve the existing handling of partial writes and stream cancellation.

### A16. Define the grace period for late-night check times

[withinCheckWindow](../src/shared/schedule.ts#L61) constructs both boundaries from the current calendar day. `23:45` is a valid setting. Its check window contains `23:59` but excludes `00:05` the following day, even though the documented grace period is 30 minutes. `effectiveRunTime` moves an overdue check to the next `23:45` slot.

Either support the previous day's window across midnight or explicitly constrain/document late times. Add a cross-midnight domain case after that policy is chosen. This is a low-frequency edge for customized schedules.

### A17. Close the gap between coding-standards and lint enforcement

An AST scan found 54 non-null assertions: 29 in production TypeScript and 25 in tests. It also found 61 top-level exported declarations without attached JSDoc, excluding additional undocumented public class members. No `any` keyword types or non-`as const` casts were found in application/test TypeScript. No module-mocking tests were found.

The vendored [assertion-comment rule](../tools/oxlint/anti-slop/rules/require-safety-comment-for-type-assertion.ts#L127) visits type casts, not non-null assertions. A green lint run therefore does not establish compliance with the user's prohibition on `!` assertions.

Enforce that prohibition explicitly and replace assertions with narrowed values, nonempty tuples, or types that capture the existing invariant. Add useful contract documentation when revising public modules; do not generate comments that merely repeat names. The stricter unused/override/fallthrough compiler checks already pass and can be enabled with little migration cost.

## Optimization opportunities

1. **Reduce the browser payload after Windows measurement.** The current local Linux staging directory contains about 393 MiB of full Chromium, 261 MiB of headless shell, and 4.9 MiB of FFmpeg. [stage-browsers.mjs](../scripts/stage-browsers.mjs) installs Chromium's default payload, while checks launch headless. Investigate staging only the required headless payload, preserving integrity hashes and packaged HTTPS smoke tests. These Linux directory sizes are not predicted Windows installer savings. The previous duplicate-copy packaging issue is already fixed.
2. **Stream the release hash.** [sign-release-manifest.mjs:27](../scripts/sign-release-manifest.mjs#L27) reads the entire installer into memory to hash it. Stream it into `createHash` and use file metadata for its size. The workflow describes an installer around 800 MB, making this a more concrete saving than micro-optimizing small arrays.
3. **Avoid repeated DOM extraction within one observation.** ePermit reads `recordFields` during observation and again for the record. WMIS reads result rows in observation, empty-result detection, and extraction. Where the same settled page is being inspected, collect one coherent result and pass it through that operation. Preserve fresh identity/fingerprint checks before an action, and do not cache across navigation.
4. **Remove the unused snapshot query before introducing caches.** The unused browser-version read above is a direct simplification. Existing row reconciliation and pending-history deduplication are worth retaining. The built renderer is about 68 KB and does not bundle Zod; code splitting or a UI framework rewrite is not supported by the measurements.
5. **Measure browser reuse and history pagination before implementing them.** A new browser per check costs startup time but provides useful isolation. Unbounded history will eventually need a limit, but this audit did not establish it as the current bottleneck. Instrument representative Windows workloads, then choose the smallest change supported by the result.
